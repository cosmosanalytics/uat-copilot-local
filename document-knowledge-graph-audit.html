Build & Audit a Knowledge Graph From Your Own Document

Paste text or upload a .txt/.md file. It's chunked, a graph of (subject, relation, object) triples is extracted chunk by chunk, and then audited by retrieving each triple's source passage again and checking whether the model still says the passage supports it. Runs entirely in your browser via WebLLM / WebGPU — the document never leaves your machine.

What "accuracy" means here — read this first: This audits faithfulness to your document, not real-world truth. A triple is scored "correct" if, when the model is shown the retrieved passage again, it agrees the passage supports that relationship — that only tells you the graph reflects what your document says, not that your document is right about the world. If your source text itself is wrong, a faithful extraction of that wrong claim still scores as correct; this tool can't and doesn't try to catch that. "RAG" here is lexical retrieval — keyword/word-overlap scoring between a query and each chunk — not embedding-based semantic search, to keep this a single-model, single-file browser app with no second model to load. Extraction uses a deliberately bounded JSON schema (max 5 triples per chunk, capped string lengths) — an earlier app in this portfolio hit a real, confirmed WebLLM/XGrammar performance bug where unbounded schemas defeat the grammar-decoding cache; bounding it avoids that. Processing is capped at the first 24 chunks (~roughly the first several thousand words) to keep this runnable in-browser; longer documents are silently truncated past that, which is disclosed in the stats panel, not hidden. Small local models will extract noisy, incomplete, or occasionally malformed triples — this is a prototype for seeing the idea work, not a production extraction pipeline.

How to read the graph

Thin gray line: the extracted graph — every triple the model pulled from the document, shown as soon as it's found, regardless of audit status
Colored line drawn on top: audit overlay — only appears once that triple has been checked at least once. Hue: faithfulness (red = audit found the passage doesn't support it → green = audit confirmed it)
Opacity of the overlay: audit coverage (how many times this triple has been re-checked against its source passage)
Safe-zone view (below): solid green = clears your chosen trust-score floor, solid red = falls below it — a binary read instead of the continuous gradient

2. Audit the graph

For each check: the triple's source chunk is retrieved again (lexical RAG), the model is shown only that passage, and asked whether it actually supports the claimed relationship. "Run faithfulness audit" samples a batch at random (can retest the same edge); "Audit every edge" instead walks the whole graph once so every edge gets at least one check.

3. Apply a safe-zone policy

The audit gives every tested edge a trust score (correct ÷ tested). This doesn't compute a threshold for you — it's a policy call you make based on how costly a wrong answer would be. The check below is deliberately pessimistic — the robust-MPC way: instead of comparing the raw score to the floor, it compares the worst-case lower bound of that score (a confidence interval that automatically widens for edges tested only a few times) to the floor. So an edge that happened to get 1/1 correct won't show as "safe" the way a well-tested 18/20 will — a lucky single audit can't fake its way past the floor. Set the floor below, and the graph splits into edges whose worst case still clears it (safe to answer from directly) and edges that don't (should be flagged or escalated to a human). Untested edges can't be judged either way yet.
