Healthcare Process Studio

11 tool calls — one per stage of a single patient's standard US insurance-based care journey (Registration → Utilization Trend Forecast → Eligibility → Prior Authorization → Clinical Encounter → Medical Coding → Claim Submission → Adjudication → Payment Posting → Denial Management & Appeals → Patient Billing). Each tool is a pure, deterministic function modeling the real math and gating rules of that stage (deductible/coinsurance/copay math, CPT/ICD-10 coding, a least-squares utilization-trend forecast, prior-auth clinical criteria, denial/appeal outcomes). The decision of which stage to run is always just a pick from a short, fixed menu — so instead of a large tool-calling-specialized model, you can either pick the action yourself from a plain menu, or route a free-text request to it with a small (<2B parameter) local instruct model reading plain text — no native tool-calling API, no large model. Run stages manually to study the logic either way. Stage order and definitions are adapted from published revenue-cycle-management and utilization-management literature (see footer for sources) and simplified for illustration — this is not medical, billing, or legal guidance.

Preauth is only required for imaging_advanced / surgery / inpatient_admission (a simplified prospective-utilization-review rule). office_visit_established never requires it.
Claim adjudication
The contracted "allowed amount" is what the payer recognizes as payable at all; the difference from the billed charge is a contractual write-off the provider absorbs — not paid by the patient. Set this to 0 to force a denial and exercise the appeals path.
Denial management — appeal
Only used if Adjudication results in a denial. Strength ≥ 0.6 overturns the denial on appeal (simplified); below that, the denial is upheld and the claim closes as a provider write-off with no plan or patient payment.

Run the case

Pick an action from the menu and click Execute — this calls the exact same stage functions shown above, directly, with no model deciding anything. It's the same job an LLM tool-calling orchestrator would do (choosing which tool to call next), just done by you from a plain menu instead of by typing a request to a model.

A small local instruct model (no native tool-calling API — just plain text in, plain text out) reads your request plus the list of valid menu actions, and replies with which one to run. That reply is matched against the same fixed menu shown above and executed the same way — the model never computes any number itself, it only decides which of the fixed actions you meant.
