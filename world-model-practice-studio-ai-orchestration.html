World Model Practice Studio

11 tool calls — one per stage of the World Model state-space chain (Aggregate → Forecast → Consensus → Disaggregate → Forecast Consumption → Dependent Demand → Firming → Capacity Pooling → Inventory → Monitor → Owner). Each tool is a pure, deterministic function. The decision of which stage to run is always just a pick from a short, fixed menu — so instead of a large tool-calling-specialized model, this edition routes free-text requests ("run stage 3", "do the whole thing") with a small (<2B parameter) local instruct model reading plain text — no native tool-calling API, no large model. The plain menu below still works too, for exact manual control.

World Model

Every engine is this same 11-stage chain, grouped here into four intuitive beats. Each tab holds that beat's editable inputs plus its stage cards — edit a field, click "Apply inputs & reset state" (it always resets the full chain, since a change anywhere downstream invalidates everything after it), then run stages manually to study the math, or use Option 1 (Menu) or Option 2 (LLM) below to run the chain.

Aggregation is fixed for this example: Group 1 = WidgetA-East + WidgetA-West, Group 2 = WidgetB-East. Note the period-8 spike in WidgetA-East — it's a deliberately injected outlier.
Forecast — outlier bounds
At k=3 with only 8 points, a single extreme value inflates its own SD estimate enough that it often escapes clipping (the classic "masking effect"). Try k=1 or 1.5 and re-run Forecast to watch it get clipped instead — and watch the downstream Capacity alert disappear.

Run the chain

Pick an action from the menu and click Execute — this calls the exact same stage functions shown above, directly, with no model deciding anything. It's the same job an LLM tool-calling orchestrator would do (choosing which tool to call next), just done by you from a plain menu instead of by typing a request to a model.
Type what you want in plain English. A small local instruct model (no native tool-calling API — just plain text in, plain text out) reads your request plus the list of valid menu actions, and replies with which one to run. That reply is matched against the same fixed menu shown above and executed the same way — the model never computes any number itself, it only decides which of the ~12 fixed actions you meant. Runs fully client-side via WebGPU.
